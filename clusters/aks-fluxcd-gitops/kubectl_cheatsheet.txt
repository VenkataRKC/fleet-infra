SCALING PODS, DEPLOYMENTS, AND STATEFULSETS - MUTATING
-----------------------------------------------------

Individual Pods cannot be scaled. Scale their owning Deployment, StatefulSet,
ReplicaSet, or another controller. A standalone Pod must be replaced by a
controller-managed workload before it can be scaled safely.

# Read-only: identify the Pod owner and current controller replica counts.
ku get pod my-pod -n oms `
  -o jsonpath='{range .metadata.ownerReferences[*]}{.kind}{"/"}{.name}{"\n"}{end}'
ku get deployment,statefulset,replicaset,hpa -n oms
ku get deployment my-app -n oms `
  -o custom-columns='NAME:.metadata.name,DESIRED:.spec.replicas,READY:.status.readyReplicas,AVAILABLE:.status.availableReplicas'
ku get statefulset my-stateful-app -n oms `
  -o custom-columns='NAME:.metadata.name,DESIRED:.spec.replicas,READY:.status.readyReplicas,CURRENT:.status.currentReplicas'

# MUTATING: scale a Deployment.
ku scale deployment/my-app -n oms --replicas=3
ku rollout status deployment/my-app -n oms --timeout=5m

# MUTATING: scale only when the current replica count is exactly 2.
ku scale deployment/my-app -n oms --current-replicas=2 --replicas=3

# MUTATING: scale a StatefulSet. Scale-down removes the highest ordinal first;
# inspect persistent volume retention and application quorum before doing this.
ku scale statefulset/my-stateful-app -n oms --replicas=3
ku rollout status statefulset/my-stateful-app -n oms --timeout=10m

# MUTATING: scale more than one controller explicitly.
ku scale deployment/frontend deployment/backend -n oms --replicas=3

# MUTATING: create an HPA for a Deployment. Metrics Server and resource requests
# must be configured. Prefer storing the HPA manifest in Git for GitOps workloads.
ku autoscale deployment/my-app -n oms `
  --min=2 `
  --max=10 `
  --cpu-percent=70

ku get hpa -n oms
ku describe hpa my-app -n oms
ku get hpa my-app -n oms --watch

# MUTATING: remove the example HPA before manually controlling replicas again.
ku delete hpa my-app -n oms


POD AFFINITY AND ANTI-AFFINITY - REFERENCE MANIFEST
---------------------------------------------------

Affinity is configured in a Pod template, not with a standalone kubectl affinity
command. For GitOps-managed workloads, commit the manifest change and let Argo CD
apply it. Use stable workload labels and a topology key present on eligible nodes.

# Read-only discovery and inspection.
ku explain deployment.spec.template.spec.affinity --recursive
ku get nodes --show-labels
ku get deployment my-app -n oms -o yaml
ku get pods -n oms -l app.kubernetes.io/name=my-app -o wide

# Example fragment under Deployment spec.template.spec.
# podAffinity prefers placement near Pods labeled app.kubernetes.io/name=backend.
# podAntiAffinity prefers spreading my-app Pods across nodes.

affinity:
  podAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 50
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: backend
          topologyKey: kubernetes.io/hostname
  podAntiAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 100
        podAffinityTerm:
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: my-app
          topologyKey: kubernetes.io/hostname

# Required anti-affinity is stricter and can leave Pods Pending when there are not
# enough eligible topology domains. Use it only when hard separation is required.

affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      - labelSelector:
          matchLabels:
            app.kubernetes.io/name: my-app
        topologyKey: kubernetes.io/hostname

# Validate and compare a complete manifest containing the fragment.
ku apply --dry-run=server -f my-app-deployment.yaml -o yaml
ku diff -f my-app-deployment.yaml

# MUTATING: direct apply. Prefer Git/Argo CD when the workload is GitOps-managed.
ku apply -f my-app-deployment.yaml
ku rollout status deployment/my-app -n oms --timeout=5m


TAINTS AND TOLERATIONS - REFERENCE MANIFEST
-------------------------------------------

A toleration permits scheduling onto a matching tainted node; it does not guarantee
placement there. Combine it with node affinity or a node selector when placement is
required. Confirm the taint key, value, and effect before adding a toleration.

# Read-only: inspect node taints and workload tolerations.
ku get nodes `
  -o custom-columns='NODE:.metadata.name,TAINTS:.spec.taints[*].key,VALUES:.spec.taints[*].value,EFFECTS:.spec.taints[*].effect'
ku describe node my-node
ku get deployment my-app -n oms `
  -o jsonpath='{range .spec.template.spec.tolerations[*]}{.key}{"="}{.value}{":"}{.effect}{"\n"}{end}'
ku explain deployment.spec.template.spec.tolerations --recursive

# Example fragment under Deployment spec.template.spec.
tolerations:
  - key: workload
    operator: Equal
    value: oms
    effect: NoSchedule

# Example toleration for a key regardless of value.
tolerations:
  - key: dedicated
    operator: Exists
    effect: NoSchedule

# Example node affinity paired with a toleration. Nodes must already have the
# workload=oms label and matching taint.
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: workload
              operator: In
              values:
                - oms
tolerations:
  - key: workload
    operator: Equal
    value: oms
    effect: NoSchedule

# Validate, diff, and then apply through the approved workflow.
ku apply --dry-run=server -f my-app-deployment.yaml -o yaml
ku diff -f my-app-deployment.yaml
ku apply -f my-app-deployment.yaml


PODDISRUPTIONBUDGET (PDB) - REFERENCE MANIFEST
----------------------------------------------

A PDB limits voluntary disruptions such as node drains. It does not protect against
involuntary node failure and does not control Deployment rolling-update behavior.
The selector must match the workload's Pod-template labels.

# Read-only: inspect labels, replica count, and existing PDBs.
ku get deployment my-app -n oms --show-labels
ku get pods -n oms -l app.kubernetes.io/name=my-app --show-labels
ku get poddisruptionbudget -n oms
ku describe poddisruptionbudget my-app-pdb -n oms
ku explain poddisruptionbudget.spec --recursive

# Example PDB: keep at least two matching Pods available.
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-app-pdb
  namespace: oms
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app.kubernetes.io/name: my-app

# Alternative: allow at most one unavailable Pod. Use either maxUnavailable or
# minAvailable, not both.
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-app-pdb
  namespace: oms
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app.kubernetes.io/name: my-app

# Validate and compare the complete PDB manifest.
ku apply --dry-run=server -f my-app-pdb.yaml -o yaml
ku diff -f my-app-pdb.yaml

# MUTATING: direct apply/delete. Prefer Git/Argo CD for managed resources.
ku apply -f my-app-pdb.yaml
ku delete poddisruptionbudget my-app-pdb -n oms

# Observe allowed disruptions before draining a node.
ku get poddisruptionbudget my-app-pdb -n oms `
  -o custom-columns='NAME:.metadata.name,MIN:.spec.minAvailable,MAX_UNAVAILABLE:.spec.maxUnavailable,ALLOWED:.status.disruptionsAllowed,CURRENT_HEALTHY:.status.currentHealthy,DESIRED_HEALTHY:.status.desiredHealthy'


POD AND RESOURCE DELETION - MUTATING
------------------------------------

Deleting a pod managed by a Deployment, StatefulSet, or DaemonSet normally causes
its controller to create a replacement. If Argo CD owns a deleted manifest, Argo
may recreate it. Inspect ownership and disruption budgets before deleting anything.

# Read-only prechecks.
ku get pod my-pod -n oms -o wide
ku describe pod my-pod -n oms
ku get pod my-pod -n oms `
  -o jsonpath='{range .metadata.ownerReferences[*]}{.kind}{"/"}{.name}{"\n"}{end}'
ku get poddisruptionbudget -n oms
ku get events -n oms --field-selector involvedObject.name=my-pod

# Preview label selection before using it with delete.
ku get pods -n oms -l app=my-app -o name

# MUTATING: gracefully delete one pod and wait for completion.
ku delete pod my-pod -n oms --wait=true --timeout=2m

# MUTATING: gracefully delete selected pods. Verify the selector above first.
ku delete pods -n oms -l app=my-app --wait=true --timeout=5m

# MUTATING: delete resources defined by a manifest or Kustomization.
ku delete -f manifest.yaml
ku delete -k infra/oms/environments/uat/my-component

# MUTATING: delete a completed Job and its owned pods.
ku delete job my-job -n oms

# Read-only: locate Failed or Evicted pods before deleting exact names.
ku get pods -A --field-selector=status.phase=Failed -o wide
ku get pods -n oms `
  -o custom-columns='NAME:.metadata.name,PHASE:.status.phase,REASON:.status.reason' `
  --no-headers

# MUTATING AND DISRUPTIVE: force deletion bypasses graceful shutdown. Use only for
# a pod confirmed stuck in Terminating after checking node and storage health.
ku delete pod my-stuck-pod -n oms --grace-period=0 --force

# HIGH RISK: never run --all until namespace and resource types are verified.
ku get pods,services -n my-namespace
ku delete pods,services -n my-namespace --all
